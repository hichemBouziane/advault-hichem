# قواعد أمان وهيكلة مشروع AdVault (Project Security & Architecture Rules)

يجب الالتزام الصارم بالقواعد الأمنية والهيكلية التالية في جميع عمليات التعديل أو الإضافة المستقبلية على الكود البرمجي وقاعدة البيانات للمشروع:

## 1. العمليات الحسابية والمالية (Database-level Math)
- يُمنع نهائياً إجراء أي عمليات تحديث أو تعديل للمحافظ أو الأرصدة (balance/payout_balance) من طرف واجهة العميل (client-side JS).
- كل العمليات المالية (الشحن، الخصم، الحجز، الاسترجاع) يجب أن تتم بالكامل عبر **زنادات قاعدة البيانات (PostgreSQL Triggers)** لضمان نزاهة العمليات الحسابية وأمانها.

## 2. عزل وحماية الجداول (RLS Policies)
- يجب إبقاء ميزة **جدار حماية السيرفر (Row Level Security - RLS)** مفعلة دوماً على جميع جداول قاعدة البيانات.
- يُمنع السماح بالقراءة العامة للبيانات للعامة. كل جدول مضاف حديثاً يجب أن يمرر هيدر التوكن المخصص `x-session-token` لمطابقته مع الجلسة قبل إرجاع السجلات.

## 3. حماية جلسات الدخول واللوحات (Session Roles Verification)
- شاشات الإدارة والتحكم للأدمن والشركاء يجب أن تفحص رتبة العميل فورياً من السيرفر عبر الـ RPC المخصص `verify_session_role` عند تحميل عناصر الـ DOM لتجنب تزوير الدور (localStorage tampering).

## 4. سرية توكنات الويب والاتصالات (No Hardcoded Tokens)
- يُمنع كتابة أي توكنات سرية (مثل توكنات بوت تليجرام، مفاتيح API، كلمات سر) داخل ملفات الجافا سكريبت بالمتصفح.
- جميع اتصالات الويب الحساسة الخارجية يجب أن تُعاد توجيهها لتتم بأمان من جهة السيرفر عبر دوال **SQL RPC** مخصصة (مثل دالة `secure_send_telegram`).
